# tools

Python 3.11+, standard library only, strict type hints. Tests: `python3 -m unittest discover -s tools/tests -t .` (PR CI runs them).

- Layout (2026-11-27): `layout.py` owns every path and module name. Statements live at `Theorems/<ab>/<hash>/Statement.lean`, attempts at `Theorems/<ab>/<hash>/attempts/<cd>/<attempt>/{Attempt.lean,attempt.toml}`, where `<ab>`/`<cd>` are the first two hex digits and hashes are 20 digits (`HASH_LEN`). `parse_path` accepts exactly those two shapes (fixed depth 4 and 7, shard checked); `check_scope`, `automerge.decide` and `check_all` all go through it. Never build a `Theorems/...` path or module by hand.
- Module paths are sharded (`Theorems.«ab».«hash».Statement`); namespaces are not (`Theorems.«hash»`, `Theorems.«hash».Attempt_<a>`). `safety.py` checks theorem imports with `layout.THEOREM_MODULE_RE`, which ties the shard to the hash.
- `migrate_layout.py` did the one-time move from 12-digit flat folders and wrote `migrations/2026-11-hash20.json` (old→new statements and attempts, plus each attempt's statement). Automerge's earned-credit parser and provenance read that map, so old merge titles and original merge dates still count. Keep the map; the site uses it for redirects.
- Shard fill is random: one directory passes GitHub's 3,000 entries at about 700k items per level, not 768k.
- `arginf.py path <hash> [<attempt>]` prints a folder; CONTRIBUTING and pr.yml use it instead of shell substrings.
- Run `python3 -m unittest discover -s tools/tests -t .` and `python3 tools/arginf.py check-all`.
- Merge queue (2026-11-27): automerge no longer merges. `automerge.enqueue` adds the `arginf:<kind>` label, then `enqueuePullRequest` with `expectedHeadOid` = the checked commit. pr.yml also runs on `merge_group` (check-all, then the full build); keep its job names (`scope`, `lean`) stable, they are the required checks.
- `ledger.py` owns "who merged what": entries come from labelled merged PRs (author, merge time and files from the API) plus automerge's pre-queue commit titles through the rename map. Never derive credit from commit authors or titles of new merges. main's `ledger` job uploads `ledger.json`; automerge reads the latest artifact (`ledger.read_ledger`), counts merges after that run with one search, and adds PRs still queued (`automerge.recent_count`). No ledger: last 24 h from the API and no earned credit (fail toward lower caps).
- Status comments (`announce.py`): one comment per PR, found by `MARKER` and authored by `github-actions[bot]` (never edit a user's copy). automerge posts "accepted, queued" after enqueueing (no badges: they can change while queued); main's ledger job (`ledger build --announce`) updates it after the merge with badges (first proof, shortest, earned credit) for entries new since the previous ledger and merged in the last 2 h. Comments quote nothing from the PR. Links: `announce.statement_url` (`https://arginf.com/theorems/<hash>`) and `announce.pr_url` (`https://arginf.com/pr/<number>`, the live tracking page).
- Stage line: every status comment carries `<!-- arginf-stage: {"v":1,"stage":…,"pr":…,"hash":…,"attempt":…,"at":…} -->` (`announce.stage_line`; values validated, fixed keys). Stages, in order: `checks` (pr.yml requested), `failed` (pr.yml failure/timed_out/startup_failure), `held` (cap, moderation or not auto-mergeable), `accepted` (before enqueue), `queued`, `merged` (ledger job), `published` (site deploy). The checks/failed steps come from automerge.yml's light `status` job (`automerge status <sha> <action>`, `github.token`, pull-requests: write only); pr.yml itself never comments. `python3 -m tools.announce published <pr>...` (env `GITHUB_REPOSITORY`, `COMMENT_TOKEN`) moves a comment from `merged` to `published` only, never posts, never touches a non-bot comment. Readers (the /pr/<n> page) must check author `github-actions[bot]` + type Bot + `MARKER` before trusting a stage line.
- Incremental CI (`incremental.py`): PR, merge-group and main checks build, kernel-check and audit only the statements a change adds (`plan` from the diff, `targets` as lake `+Module` targets). Never call `lake build`, `arginf.py kernel` or `audit` with no arguments in CI: no arguments means everything. Contributor PRs never run the planner (it runs only for merge groups and maintainer `infra/*` branches).
- `audit-cache.json` (on the index branch, next to `index.json`) records passes per environment key = hash of `lean-toolchain` + `lake-manifest.json`. A bump changes the key, so `full-check.yml` rebuilds everything as a capped matrix over shards and resumes daily from the cache. Only passes are cached; failed statements stay pending and open a `full-check-failed` issue. Not the Actions cache, which is for Lean dependencies.
- `arginf.py`: hashing, scope checks, attempts, `index` (index.json, version 2).
- `readings.py`: pinned model + llama.cpp runner. `prepare()` returns an `Engine` (verified binary + weights); `complete()` runs one deterministic completion. `statement_lean()` is the shared view of a statement that every model prompt uses.
- `areas.py`: area labels. `AREAS` is the fixed list (arXiv codes). `parse_codes()` keeps only known codes, in reply order, capped at `MAX_AREAS`; `embed()` re-checks them, so nothing but fixed labels reaches the site. Published as `areas.json` on the `index` branch and as `index.areaList` plus `theorem.areas = {codes, model, modelSha256, runtime, cpu, promptSha256} | null`.
- Changing `AREAS` or `PROMPT` changes `promptSha256`, so CI relabels every statement on the next merge (one short completion per statement, but the prompt is reprocessed each time, so check run time before growing the catalog or list a lot).
- Model output is untrusted text: `raw` stays in areas.json for audit and is never embedded in index.json; the site renders only codes from `areaList`.
- Published data (`data.py`, `publish.py`, 2026-11-27): the site reads `manifest.json` plus content-hashed files (`summary/<ab>.<c>.json`, `statements/<ab>/<hash>.<c>.json`, `search…`, `graph/areas…`, `reviews…`, `ledger…`) from the `data` branch, which GitHub Pages serves at data.arginf.com. Every name but the manifest is content-hashed (cache forever); a summary row carries its detail file's `<c>`; the manifest lists every other file. `publish build` rebuilds only statements changed since the manifest's commit, plus the lemmas they import (dependents change); everything else is carried forward. Superseded files go to `meta/retired.json` and are deleted on the next build. A build with nothing new changes no file, so nothing is pushed.
- `publish.yml`: after each verified main run, at least 6 minutes after the last publish (Pages builds from the branch: about 10 builds an hour), one commit and one push; then waits for the Pages build and runs `announce published` for the affected PRs. `enrich.yml` adds readings and area labels (at most 50 statements per run) as a second publish, so the model is never on the merge→site path. Weekly squash of the data branch. `index.json` on the `index` branch keeps being published by main.yml until the site has switched.
- Caches live in the data tree: `cache/readings/<ab>.json`, `cache/areas/<ab>.json`, `cache/audit/<ab>.json` (main and full-check read them, falling back to the index branch's audit-cache.json until the data branch exists).
- `guard.py`: size and runway from `meta/size-history.json`; 40% of 1 GB or <180 days opens a `data-size` issue for Adam, 60% or <60 days marks it urgent and fails the `data-size` job. Never blocks publishing. The S3 + CloudFront stack and runbook are in arginf/arginf (`infra/arginf_infra/data_host.py`, `docs/data-host-runbook.md`).
- `reviews.py`: CI's list of open PRs whose scope and lean checks passed ("#n by @login" facts only), so browsers never call the GitHub API.
